# Deterministic local demonstration

Run `make demo` from the repository root. The command builds both MockBridge contracts, creates a fresh temporary PostgreSQL 18.6 database, and starts source Anvil 1.8.5 (`31337`) and destination Anvil 1.8.5 (`31338`). It requires no public network or manual database edits. Foundry 1.8.5 is used from the host or fetched as a checksum-verified official archive.

The single scenario emits a source message, observes `SOURCE_SEEN`, reaches source finality and `SOURCE_FINAL`, activates `RELAY_PENDING`, advances a controlled 30-second SLA, opens one `STUCK` episode, and delivers one alert to an in-memory deterministic sink. A late destination execution reaches `DEST_SEEN` and then `COMPLETED`. The scenario adds an identical destination execution and then a conflicting one, checks fail-closed anomalies, and rolls back that fork. It exercises source reorg and re-inclusion, destination reorg and re-execution, a fresh watcher using the durable checkpoint, and failover when one configured RPC reader fails. API readiness and metrics are checked. A second message is executed on the destination first and converges after source catch-up.

`out/phase5/demo.json` contains exact tool versions, topology, policy, steps, counts, histograms, checksum, and wall duration. The test and evidence validator require two messages, eight retained observations, 15 business transitions, four anomaly episodes (`STUCK`, `DUPLICATE_EXECUTION`, `CONFLICT`, `REORGED`), one alert episode, no open `STUCK`, two completed messages, and no consecutive duplicate business transition. The deterministic count checksum is `79c87f304c3a1eb24633b7c4f31d9e3d8ecd07c2b886f6e1b74a9efa22aa2ec4`. A mismatch fails the command. Evidence is regenerated by the command and is not committed as a static result.

The source fixture is deployed at block 1 with genesis `0x3e8b48d8cbf5dfa86c941f2c1821786417d34ef516ef1a336fdb035f984f89e9`; the destination fixture is independently deployed at block 1 with genesis `0xb6992ddc6d2e12e25f20be8c5857fbb37b84072a30a33fc6749bc3ce23f3c52e`. Both local contract addresses are `0x5FbDB2315678afecb367f032d93F642f64180aa3`, obtained from their separate receipts.

## Service settings

For a separately running local service, set `BRIDGEWATCH_DATABASE_URL`, chain IDs, contracts, genesis hashes, start blocks, source and destination confirmations, `BRIDGEWATCH_MAX_REORG_DEPTH`, `BRIDGEWATCH_RELAY_SLA_SECONDS`, and `BRIDGEWATCH_RELAY_POLICY_VERSION`. Configure either `BRIDGEWATCH_SOURCE_RPC_ENDPOINTS` and `BRIDGEWATCH_DESTINATION_RPC_ENDPOINTS` as `id=url,id=url` lists or the single endpoint `BRIDGEWATCH_SOURCE_RPC_URL` and `BRIDGEWATCH_DESTINATION_RPC_URL`. The deterministic fixture uses three confirmations on each chain, depth eight, SLA 30 seconds, and policy version one. The runner defaults to `127.0.0.1:8080`; `BRIDGEWATCH_LISTEN_ADDR` overrides it. `BRIDGEWATCH_ALERT_WEBHOOK_URL` is optional; without it alerts remain in the durable outbox.

The read-only API exposes `/v1/messages`, `/v1/anomalies`, `/v1/status`, `/health/live`, `/health/ready`, and `/metrics`. The [OpenAPI contract](../api/openapi.yaml) defines filters and response shapes. Keep this service and its database behind trusted network access when using non-local data. The fixture contracts emit events; they contain no custody, validators, relay service, or proof logic.
