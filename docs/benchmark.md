# Local benchmark methodology

Run `make benchmark` for three fresh 80-message repetitions, or `make benchmark-smoke` for one 20-message correctness run. Each repetition uses a fresh PostgreSQL 18.6 cluster and the same in-process deterministic fork readers used by the watcher tests. This measures the source and destination watcher, PostgreSQL ingestion and projection, SLA classification, and alert outbox under a zero-delay RPC fixture. It does not measure public RPC service, chain block production, network tail latency, a remote webhook, or production throughput.

Each full repetition has 80 source messages, 76 destination executions (including four same-message repeats), a 5% duplicate rate, no conflicting duplicates, and a 10% delayed ratio. Source and destination have three-confirmation policies. One watcher per chain processes ranges of eight blocks with a PostgreSQL pool limit recorded in evidence. Four groups of ten destination messages are observed and finalized; the controlled clock then opens eight STUCK episodes. Workload metadata records worker count, range size, pool size, RPC latency and failure fixture, and policy.

Raw JSON files at `out/phase5/benchmark-80-run-01.json` through `-03.json` record OS, architecture, CPU, memory, Go, PostgreSQL, and Anvil tool versions; count and state histograms; an ordered SHA-256 of message IDs and payload hashes; messages/s; observation-to-correlation and completion classification p50/p95; rows/s; CPU seconds; process memory; and total duration. `benchmark-80-summary.json` reports the median of all three valid runs and includes every raw rate. The measurement windows are local workload wall times. Correlation latency is measured from completion of source catch-up to a destination group being observed; completion latency extends to its finalization. These figures include batch ordering and are not per-message network latency.

A run is valid only when all checks pass: 80 normalized messages, 156 retained observations, 276 transitions, exact state histogram (`COMPLETED` 68, `RELAY_PENDING` 8, `SOURCE_SEEN` 4), four duplicate-execution anomalies, eight STUCK anomalies, eight alert episodes, zero consecutive duplicate business transitions, and exact message/payload checksum. The 20-message smoke run requires 39 observations and 68 transitions with the same proportions. A failed run is written as invalid and its throughput is excluded from the median.
